# Native PlayCanvas knee art review — provisional, not approved

Run from the renderer repository root: `node scripts/review-knee-art-browser.js`. Requires the neighboring candidate art repository, local `node_modules`, and Playwright Chromium. The script reads four *provisional* candidate manifests/GLBs, checks their declared SHA-256/byte length, serves the unchanged existing renderer testbed on an ephemeral loopback port, loads GLBs into temporary PlayCanvas containers in browser test code, and captures the existing facade's PlayCanvas application/camera/track/target layer. It overwrites only the 44 PNGs and `bounds.json` in **this review output directory** on repeat runs; do not use it to export/release assets. No test page or production package changes.

Each target variant (`open-prong-v1`, `chevron-v1`, `turtle-shell-strap-v1`) appears in 12 labeled views: left/right lowest outside cell (8/11), FAR (1400 ms), NEAR (420 ms), HIT distance (0 ms), at landscape 844×390 and phone portrait 390×844. `comparison-punch` (real pinned arrow) and paired `comparison-guard` (real pinned shields) are drawn by the ordinary Boxing Grid scene model; the unmodified pinned blue glass four-column track and canonical camera are native. The candidate is **independently staged**, using grid X/Y from `model.grid` and Z/scale from the renderer's own punch scene object at the same beat time. This is a visual relative-placement preview, not an authored knee beat, hit-state feedback, judge, or gameplay. Side colors are illustrative cyan/coral. The front of each candidate faces local/world −Z per its provisional manifest; native camera sits at world +Z, so the camera sees the *back* of the candidate. This observed orientation conflict must be reviewed and resolved before actual implementation; do not assume these captures prove the intended front-facing knee silhouette. A rotation would be another unapproved visual choice, so this review deliberately does not silently rotate the model. In these captures the turtle-shell target's luminous central oval looks more like a rear/underside than its intended broad domed front, especially at FAR; compare against the source `views/front.png`.

The eight `pad-*` PNGs show the same provisional pad instanced left/right on **simple illustrative native PlayCanvas cylinder legs**, straight/lowered or bent/raised, in cyan/coral and amber/violet pairs at both viewports. These are not measured pose landmarks, real anatomical fit, MediaPipe tracking, physical ergonomics, collider geometry, or scored gameplay. The pad front likewise follows its authored −Z, so rear/strap visibility in the athlete-facing camera is especially relevant. Front/side/rear Blender source renders and Derrick's three concept pictures should be reviewed separately beside these images; this harness does not claim a full 360° posed-leg review or embed the private concepts.

`bounds.json` records the provisional GLB hashes, per-view projected candidate geometry boxes in CSS pixels, actual framebuffer size, camera, native asset IDs, candidate-vs-absent framebuffer pixel delta, visible track/cue pixel checks, and illustrative pad/leg delta. Chromium runs DPR1 at landscape and browser DPR3 on phone, but the renderer's current **canonical DPR cap is 2**, so actual phone WebGL backing is 780×1688; saved review PNGs use CSS scale 390×844 for direct comparison. This cap is a real renderer constraint, not changed for the review. Tests require every candidate's projected box to be onscreen, every candidate to change actual framebuffer pixels, the real track and cue pixels to be nonblank, every illustrative pad scene to change pixels, and PNG dimensions to match the labeled viewport. These assertions establish visibility, not legibility or semantic knee recognizability. FAR in landscape is only ~15–21 CSS px wide (see `bounds.json`), and the open-prong example is partially hidden by the track edge in the inspected screenshot; visual readability remains an unresolved human concern. Derrick owns both separate pad `.9` and target `.10` decisions. Both remain OPEN. No candidate is approved, immutable, integrated or published.
